# Architecture and Trust Boundaries — Continua

## Application shape

- Next.js 15.5.29 App Router application with one API route: `GET /api/health`.
- UI is static/demo shell. No authentication, user accounts, database, or mutation endpoints are implemented.
- Synthetic data is generated by `lib/generator` and stored under `data/`.
- Benchmark labels and contracts are stored under `data/eval-set`.

## Trust boundaries

1. Browser/user (untrusted) -> Next.js pages and `/api/health`.
2. Operator/CLI (trusted local) -> scripts reading/writing `data/`, `artifacts/`, and benchmark files.
3. Environment (semi-trusted configuration) -> `lib/config/env.ts`.
4. Repository consumers (unknown trust) -> committed synthetic data and benchmark labels.

## Security-relevant controls observed

- `next.config.ts` disables `poweredByHeader` and sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`.
- `lib/config/env.ts` separates server config from public config via `toPublicConfig`.
- Logger redacts field names matching key/secret/token/password/authorization.
- Leakage audits prevent runtime imports of generator and benchmark labels.
- Synthetic safety audit checks for PHI-like patterns and real organizations.
- Secret scan checks tracked code and `.env.example`.
- Schemas validate inputs with Zod in tests and generation scripts.

## Gaps

- No Content-Security-Policy or HSTS header.
- `artifacts/` is not gitignored.
- CI omits Phase 3 benchmark validation, leakage, and hash gates.
- Evaluator and benchmark-bundle code lives under `lib/`, making it importable by runtime despite audit conventions.
- Benchmark labels are committed in the repository.
