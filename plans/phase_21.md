Continua Phase 21: Demo, Storytelling & Judge Defense

Phase 20 gets Continua submitted. Phase 21 determines whether judges actually understand why it deserves to win.

By this point, adding features is dangerous. The remaining competitive advantage comes from compression: turning months of architectural depth into a story a judge understands in seconds, while keeping enough evidence behind it to survive aggressive technical, healthcare, business, and Responsible-AI questions.

Phase 21 mission: Make Continua effortless to understand, memorable after many competing demos, technically defensible under questioning, and impossible to knock over with obvious objections.

21.22 Technical Question 1
"Isn't this just an LLM wrapper?"

Answer:

"No. The LLM has one constrained job: turn messy text into source-linked structured events. Gap detection, evidence verification, and workflow priority are deterministic. That separation lets us measure extraction and reasoning independently."

Then methodology if asked.

21.23 Technical Question 2
"Why use an LLM at all?"

"Because the messy part is the language variation across fragmented records: abbreviations, different note styles, provider terminology, and historical references. Deterministic rules work well after that information has been normalized into typed events."

Good architecture justification.

21.24 Technical Question 3
"Why not let the LLM reason end-to-end?"

"We benchmark an LLM-only baseline separately. Continua intentionally limits generative authority because care-gap decisions benefit from deterministic temporal rules, reproducibility, and inspectable reasoning. The benchmark tells us the actual quality trade-off."

Use Phase-9 comparison only if actually performed.

21.25 Technical Question 4
"How do you prevent hallucinations?"

Avoid:

"We use good prompts."

Use:

"Prompting is only the first layer. Extracted events need source-document provenance, user-visible gaps must pass independent evidence verification, and anything that fails those checks is suppressed rather than displayed."

Much stronger.

21.26 Technical Question 5
"What if the model misses a consult?"

"That's one of the important failure modes. Extraction recall is measured separately, and incomplete processing prevents us from safely making absence-based claims. In production we'd also need stronger completeness guarantees from the EHR data source."

Excellent honest answer.

21.27 Technical Question 6
"How do you distinguish duplicate data from duplicate testing?"

"We normalize distinct clinical occurrences before the duplicate detector runs. A lab copied into a later note is treated as another reference to the same occurrence, while two genuinely distinct test events remain separate. We also use explicit-series safeguards for planned serial testing."

This demonstrates depth.

21.28 Technical Question 7
"Why not use FHIR?"

"FHIR is a production ingestion path, not the differentiation we're demonstrating here. The prototype focuses on what happens after fragmented information arrives: reconstructing a longitudinal journey, finding unresolved coordination issues, grounding them, and prioritizing review."

Do not imply FHIR is unnecessary.

21.29 Technical Question 8
"Why JSON cache instead of a real database?"

"The official judge path uses a validated immutable snapshot because reproducibility and demo reliability matter more than database complexity here. The domain uses repository interfaces, so a production persistence implementation can replace the JSON repository without changing the API or UI."

Excellent.

21.30 Benchmark Question 1
"How do you know it's accurate?"

"We generated an 80-patient synthetic dataset with planted ground truth before running the system, froze the benchmark, held patients out from development, and report precision, recall, and F1 separately for each supported gap type."

Then show actual metrics.

21.31 Benchmark Question 2
"Isn't synthetic data too easy?"

"That's a real limitation, so we deliberately added hard negatives such as completed referrals, telehealth consults, legitimate serial labs, copied records, medication stops, aliases, and tests just inside or outside timing windows. We also state clearly that synthetic performance is not clinical validation."

Strong.

21.32 Benchmark Question 3
"Did you tune the benchmark until you passed?"

"No. Ground truth and evaluation semantics are versioned independently. Development uses a development partition; final reported results come from the frozen held-out partition. If benchmark semantics change, it requires a new benchmark version."

If that exact discipline was actually executed.

21.33 Benchmark Question 4
"What does 100% grounding mean?"

Answer extremely carefully:

"It does not mean 100% clinical accuracy. It means that every gap we displayed in that benchmark run passed all required source-document, patient-ownership, span, policy, and absence-evidence checks. Detection precision and recall are reported separately."

This answer is important.

21.34 Benchmark Question 5
"Where does the system still fail?"

Never say:

"It doesn't."

Use Phase-14 actual top failures.

Template:

"Our largest remaining failure category is [actual]. The layered evaluation lets us identify whether the miss came from extraction, normalization, detection, or evidence suppression. That's exactly why we don't report one generic accuracy number."

Then give actual example.

21.35 Healthcare Question 1
"Is this medical advice?"

"No. Continua is workflow decision support for a care coordinator. It surfaces an issue and the supporting records for verification. It does not diagnose, prescribe, determine treatment, or autonomously act on the patient."

21.36 Healthcare Question 2
"Can this be used on real patients now?"

"No. This version is a synthetic-data prototype. Real deployment would require standards-based EHR integration, security and privacy controls, health-system governance, real-data retrospective validation, human-factor evaluation, and prospective testing."

Clear.

21.37 Healthcare Question 3
"Are you HIPAA compliant?"

"We don't make that claim. The public MVP intentionally processes synthetic data only and contains no real PHI. A real deployment would require the full organizational, technical, vendor, access-control, audit, and risk-management work appropriate to handling protected health information."

Correct posture.

21.38 Healthcare Question 4
"What if the oncology visit happened somewhere else?"

"That's exactly why our wording says 'not found in the available records,' rather than claiming the visit never happened. The coordinator sees that limitation directly in the evidence view."

One of our best answers.

21.39 Healthcare Question 5
"Is a repeat CBC always unnecessary?"

"No, and Continua doesn't claim that. It surfaces a possible repeat under the benchmark rules and asks the coordinator to review whether it was intended. Explicit scheduled series are suppressed."

Perfect.

21.43 Business Question 4

Strong product differentiation.

21.44 Competitive Question: Epic

Do not attack Epic inaccurately.

"EHRs are essential systems of record and already contain many coordination capabilities. Continua's prototype explores a narrower synthesis layer: reconstructing fragmented cross-provider journeys, detecting specific unresolved continuity patterns, grounding those patterns to evidence, and prioritizing them for review. In production, we'd expect integration with existing EHR workflows, not replacement."

Much more credible.

21.45 Competitive Question: Abridge-style Clinical AI

"Clinical documentation assistants primarily focus on converting an encounter into usable clinical documentation. Continua's problem begins across encounters and providers: what coordination issue becomes visible only when you reconstruct the longitudinal journey?"

Avoid claiming competitors do nothing similar unless verified.

21.46 "Can't the EHR Rules Engine Do This?"

"Some individual rules absolutely can, and that's intentional. Our contribution is the combination: extracting usable structure from fragmented text, normalizing cross-provider events, running auditable temporal rules, verifying every displayed claim to source evidence, and turning those verified issues into one coordinator workflow."

Excellent.

21.47 Responsible-AI Question
"Why should I trust AI in this workflow?"

"You shouldn't trust it purely because it's AI. That's why Continua limits AI authority. The model extracts source-linked facts; deterministic systems handle gap logic, evidence verification, and priority; and the coordinator remains the final decision-maker."

Probably our best Responsible-AI answer.

21.48 Fairness Question

"priority-v1 doesn't use protected demographics or diagnosis-specific bonuses. We run controlled invariance tests where demographic fields change while gaps remain identical. That tests the ranking implementation, but we don't claim it proves fairness in a real patient population."

Precise.

21.49 Security Question
"Where does patient data go?"

For current MVP:

"The submitted demo contains synthetic data only. In live extraction development mode, synthetic document text is sent to the configured extraction provider. The official judging path uses the frozen validated cache and does not require live model calls."

Excellent technical transparency.

21.50 Reliability Question
"What happens if the AI API goes down?"

"The official demo and coordinator read path continue working because benchmark-qualified intelligence is stored in an immutable validated cache. Live extraction is separated from the read experience."

This shows mature architecture.
